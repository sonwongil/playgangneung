좋습니다. 지금 진단은 맞습니다.

다만 이번 리빌딩은 기존 문제를 다시 패치하는 작업이 아닙니다.
그리고 지금 단계에서 바로 구현하지 마세요.

이번 단계의 목적은 다음입니다.

1. 기존 코드를 어떻게 처리할지 먼저 분류한다.
2. 그 다음 새 표준 스택이 최적으로 작동할 환경을 설계한다.
3. 실제 수정, DB 변경, push, 운영 서버 변경은 하지 않는다.
4. 먼저 설계 보고서만 작성한다.

## 1. 기존 코드 처리 기준

기존 코드는 아래 네 가지로 분류하세요.

### 반드시 유지할 것

* 기존 DB 데이터
* 기존 콘텐츠 데이터
* 로그인/관리자 인증 중 검증된 부분
* Meta 광고 API 연동 중 검증된 코드
* 결제 연동 중 검증된 코드
* 기존 백업·배포·검증 스크립트
* 운영상 주의사항

### 선별 이식할 것

* 기존 feed API 중 재사용 가능한 부분
* 기존 content/event 구조 중 필요한 필드
* 기존 강릉노트 개념
* 기존 TOP5 개념
* 기존 이미지 처리 중 정상 동작하는 부분
* 기존 Meta 캠페인·광고 생성 로직 중 검증된 부분
* 기존 결제 상태 처리 로직 중 재사용 가능한 부분

### 격리할 것

* 기존 관리자 화면
* 기존 홈 화면
* 기존 복잡한 입력 폼
* 기존 피드·광고·강릉노트가 뒤섞인 화면 로직
* 기존 PWA 설정
* 기존 편집기 삽입 시도 코드
* 기존 광고 화면 UI

### 폐기 후보

* 기존 화면에 계속 덧붙인 UI 코드
* 검증되지 않은 직접 제작 컴포넌트
* 복잡해진 관리자 입력칸 구조
* 억지로 끼워 넣은 편집기 구조
* 소식제보 1차 메뉴
* 지도 직접 삽입 모듈
* 기존 광고 신청 화면 중 운영 흐름과 맞지 않는 부분

## 2. 새 표준 스택

리빌딩 표준 스택은 아래로 확정합니다.

* 전체 UI: shadcn/ui
* 관리자 대시보드: satnaing/shadcn-admin
* 강릉노트 편집기: BlockNote
* 관리자 테이블: TanStack Table
* 광고 성과 차트: Recharts
* 이메일 보고서: Resend 우선, 기존 SMTP 안정 시 Nodemailer 대안
* PWA: vite-plugin-pwa + Workbox
* 지도: 도입하지 않음

## 3. 선결정 항목 기본 방침

아래 항목은 임의 구현하지 말고, 현재 상태와 추천안을 보고하세요.

### 인증 방식

기본 방침은 Clerk 유지입니다.
자체 세션 전환은 1차 리빌딩에서 보류합니다.

보고할 것:

* Clerk 관련 파일 목록
* 관리자 접근 제어 방식
* 자체 세션 코드가 남아 있는지
* Clerk 유지 시 충돌 위험

### 상태관리

기본 방침은 TanStack Query 중심입니다.
Zustand는 1차 리빌딩에서 도입하지 않습니다.

보고할 것:

* 현재 TanStack Query 사용 위치
* 불필요한 로컬 state가 많은 파일
* 전역 상태가 정말 필요한 영역

### 라우팅

현재 wouter가 사용 중이라면 1차에서는 유지 검토합니다.
라우터 교체는 별도 단계로 보류합니다.

보고할 것:

* 현재 라우팅 구조
* 새 모듈을 wouter로 감당 가능한지
* 라우터 교체가 필요한 위험 요인

### BlockNote 범위

BlockNote는 관리자 전체가 아니라 강릉노트 본문 편집 전용입니다.

기존 admin-event-detail.tsx에 다시 억지 삽입하지 마세요.

새 구조는 다음을 기준으로 제안하세요.

* GangneungNoteEditor
* GangneungNoteViewer
* GangneungNoteForm
* GangneungNoteMetaFields
* GangneungNotePreview

### DB 스키마

기존 DB는 보존합니다.
직접 삭제하거나 마이그레이션 실행하지 마세요.

보고할 것:

* 콘텐츠 관련 테이블
* events/content/feed/TOP5 관련 테이블
* 광고 관련 테이블
* 결제 관련 테이블
* Meta 관련 테이블
* 강릉노트 중심으로 통합 가능한 필드
* 새로 필요한 필드
* 마이그레이션 위험

## 4. 새 PLAY강릉 구조

새 구조는 아래 흐름을 기준으로 합니다.

강릉소식 수집함
→ 관리자 검토
→ 강릉노트 초안 전환
→ 관리자 수정
→ 오늘의 강릉소식 선정
→ 홈 상단 5개 노출
→ Facebook/Instagram 발행
→ 필요 시 Meta 광고 확장

홈 하단에는 광고 회원 소상공인 카드가 순환 노출됩니다.
카드를 누르면 외부 링크가 아니라 PLAY강릉 내부 업체 소개 랜딩 페이지로 연결됩니다.

소식제보 메뉴는 1차 리빌딩에서 제외합니다.

지도 API는 도입하지 않습니다.
주소 텍스트, 주소 복사, 네이버지도/카카오맵/구글맵 외부 링크만 제공합니다.
