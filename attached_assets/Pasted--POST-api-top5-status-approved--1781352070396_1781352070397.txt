보고 확인했습니다.

기존 `POST /api/top5`가 저장 시 포함된 이벤트의 status를 자동으로 `approved`로 변경하는 부작용을 발견한 것은 매우 중요합니다.

이 때문에 기존 API를 그대로 사용하는 1안은 승인하지 않습니다.
또한 기존 API의 자동 승인 코드를 제거하는 2안도 승인하지 않습니다. 기존 `/admin` 화면이나 기존 운영 흐름에 영향을 줄 수 있기 때문입니다.

따라서 **3안 — 새 API 생성**으로 진행합니다.

---

# Phase 1-E2 승인

## `/admin/v2` 전용 daily_top5 저장 API 생성

이번 단계의 목표는 기존 `/api/top5`를 건드리지 않고,
`/admin/v2/today` 화면에서만 사용할 수 있는 **status 변경 없는 daily_top5 저장 API**를 만드는 것입니다.

---

## 1. 선택한 방식

선택: **3안 — 새 API 생성**

이유:

1. 기존 `/api/top5`의 동작을 바꾸지 않음
2. 기존 `/admin` 화면에 영향 없음
3. `events.status`를 변경하지 않음
4. `events` 테이블을 수정하지 않음
5. `/admin/v2`에서만 안전하게 사용할 수 있음
6. 우리가 정한 “daily_top5 저장만 허용” 원칙에 맞음

---

## 2. 새 API 요구사항

새 API 이름은 아래 중 하나로 제안하고, 현재 라우트 구조에 가장 자연스러운 것을 선택하세요.

추천:

```text
POST /api/top5/v2
```

또는

```text
POST /api/top5/save-only
```

단, 이름은 명확해야 합니다.

이 API는 다음 작업만 해야 합니다.

1. `daily_top5` 저장
2. 날짜별 items 저장
3. 슬롯 순서 유지
4. 저장 후 저장된 결과 반환

이 API는 절대 다음 작업을 하면 안 됩니다.

1. `events` 테이블 수정 금지
2. `events.status` 변경 금지
3. `approved` 자동 변경 금지
4. `published` 변경 금지
5. 홈 화면 코드 수정 금지
6. SNS 발행 금지
7. Meta API 호출 금지

---

## 3. 기존 API 보존 원칙

기존 API는 절대 수정하지 마세요.

특히 아래 기존 API는 그대로 유지합니다.

```text
POST /api/top5
```

기존 `/admin` 화면이나 기존 운영 흐름이 이 API에 의존하고 있을 수 있으므로,
자동 승인 로직을 제거하지 않습니다.

이번 작업은 `/admin/v2` 전용 새 API를 추가하는 방식으로만 진행하세요.

---

## 4. 저장 request body 구조

기존 `daily_top5` 구조와 호환되도록 하세요.

예상 구조:

```json
{
  "date": "2026-06-13",
  "items": [
    { "eventId": "event-id-1", "rank": 1 },
    { "eventId": "event-id-2", "rank": 2 },
    { "eventId": "event-id-3", "rank": 3 }
  ]
}
```

단, 실제 기존 `daily_top5` 구조가 다르면 기존 구조를 우선하세요.

---

## 5. `/admin/v2/today` 저장 버튼 동작

`/admin/v2/today`의 저장 버튼은 새 API만 사용하세요.

동작 순서:

1. 현재 슬롯 확인
2. 선택 항목이 0개이면 저장 차단
3. 선택 항목이 5개 초과이면 저장 차단
4. 빈 슬롯은 제외
5. 남은 슬롯의 순서를 1부터 다시 정리하거나, 기존 슬롯 순서를 유지하는 방식 중 기존 구조와 맞는 방식을 선택
6. 새 API 호출
7. 저장 성공 toast 표시
8. 다시 `GET /api/top5?date=YYYY-MM-DD`로 재조회
9. 화면 갱신
