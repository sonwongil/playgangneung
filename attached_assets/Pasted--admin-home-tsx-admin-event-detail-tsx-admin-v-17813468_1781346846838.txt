## 1. VPS 운영 DB 확인

보고서에서 가장 중요한 미확인 사항은 운영 DB 위치입니다.

다음을 확인해 주세요.

1. VPS의 실제 `DATABASE_URL` 호스트가 어디인지
2. `localhost` 또는 `127.0.0.1`이면 VPS 자체 PostgreSQL인지
3. 외부 호스트이면 Replit 또는 외부 DB인지
4. Replit 개발 DB와 VPS 운영 DB가 같은 DB인지 다른 DB인지
5. 현재 실제 운영 데이터가 어느 DB에 있는지

주의사항:

* 비밀번호, 토큰, 전체 DATABASE_URL 원문은 보고하지 마세요.
* 호스트 유형만 마스킹해서 보고하세요.
* DB 접속, 조회, 수정, 마이그레이션은 하지 마세요.
* `cat .env` 전체 출력 금지.
* 필요한 경우 `DATABASE_URL`의 host 부분만 안전하게 마스킹해서 확인하세요.

보고 예시:

```text
VPS DATABASE_URL host: localhost
판단: VPS 자체 PostgreSQL로 추정
운영 DB 기준: Cafe24 VPS DB
Replit DB와 운영 DB: 분리 추정
```

또는

```text
VPS DATABASE_URL host: 외부 PostgreSQL 호스트
판단: 원격 DB 사용
운영 DB 기준: 외부 DB
Replit DB와 동일 여부: 추가 확인 필요
```

## 2. SNS 발행 postId 저장 방식 제안

현재 Facebook/Instagram 발행 성공 후 postId가 DB에 저장되지 않는 문제는 리빌딩 전에 구조를 정해야 합니다.

저는 `events` 테이블에 `facebook_post_id`, `instagram_post_id`를 추가하는 방식보다, 별도 `publish_log` 테이블 방식을 우선 검토합니다.

이유:

1. Facebook, Instagram, 향후 카카오/네이버 등 채널 확장 가능
2. 단일 콘텐츠가 여러 번 발행될 수 있음
3. 실패 로그 저장 가능
4. 재발행 이력 관리 가능
5. TOP5 캐러셀 발행과 단일 발행을 모두 기록 가능

다음 두 안을 비교해서 보고해 주세요.

### A안: events 테이블에 필드 추가

* `facebook_post_id`
* `instagram_post_id`
* `published_at`

장점, 단점, 마이그레이션 위험을 보고하세요.

### B안: publish_log 테이블 신설

예시 구조:

```text
publish_log
- id
- event_id
- channel
- publish_type
- post_id
- post_url
- status
- error_message
- published_at
- created_at
```

장점, 단점, 마이그레이션 위험을 보고하세요.

추천안도 함께 제시하세요.

이번 단계에서는 테이블 생성이나 마이그레이션을 실행하지 마세요.
구조 제안만 하세요.

## 3. PWA display 설정 확인

현재 `display: standalone` 때문에 PWA 설치 실행 시 크롬 UI가 사라지는 것은 정상일 수 있습니다.

다만 일반 크롬 접속에서도 크롬 메뉴가 덮이는지 확인이 필요합니다.

다음을 보고하세요.

1. 현재 manifest의 `display` 값
2. 일반 Chrome 브라우저 접속 시 주소창/메뉴가 보이는지
3. 홈 화면 바로가기 또는 PWA 설치 실행 시 주소창/메뉴가 사라지는지
4. `standalone`, `minimal-ui`, `browser` 각각의 영향
5. PLAY강릉에 추천하는 1차 설정
6. 변경 시 예상 부작용

이번 단계에서는 PWA 설정을 변경하지 마세요.
진단과 추천만 보고하세요.
