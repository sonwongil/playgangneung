보고서 확인했습니다.
전체 방향은 대체로 맞습니다.

특히 기존 admin.tsx, home.tsx, admin-event-detail.tsx를 동결하고, /admin/v2를 병렬로 구성하자는 방향은 기존 코드에 다시 예속되지 않기 위한 좋은 접근입니다.

다만 아직 Phase 1 구현 승인은 하지 않습니다.
구현 전에 아래 보완 보고서를 먼저 작성해 주세요.

## 1. 운영 DB 위치 재확인

보고서에 “PostgreSQL (Replit managed)”라고 되어 있는데, 현재 PLAY강릉은 Cafe24 VPS 전환 이후 운영 구조를 기준으로 보고 있습니다.

따라서 다음을 먼저 명확히 확인해 주세요.

1. 현재 실제 운영 DB가 Replit managed PostgreSQL인지
2. Cafe24 VPS PostgreSQL인지
3. 현재 Replit DB와 VPS DB가 각각 어떤 역할인지
4. GitHub / Replit / VPS 중 어느 쪽이 현재 운영 기준 데이터인지
5. 리빌딩 작업에서 절대 건드리면 안 되는 DB가 무엇인지

DB 위치와 기준이 불명확하면 리빌딩 중 가장 큰 사고가 날 수 있습니다.

이번 단계에서는 DB 변경, 마이그레이션, 삭제, 초기화는 절대 하지 마세요.

## 2. Phase 1 구현 전 보완해야 할 핵심 흐름

현재 보고서는 강릉노트 편집기와 새 관리자 화면 중심으로 정리되어 있습니다.

하지만 PLAY강릉 리빌딩의 핵심 흐름은 다음입니다.

강릉소식 수집함
→ 관리자 검토
→ 강릉노트 초안 전환
→ 관리자 수정
→ 오늘의 강릉소식 선정
→ 홈 상단 5개 노출
→ Facebook/Instagram 발행
→ 필요 시 Meta 광고 확장

따라서 Phase 1 전에 아래 모듈들이 새 /admin/v2 구조 안에서 어떤 순서로 들어갈지 다시 정리해 주세요.

1. 강릉소식 수집함
2. 강릉노트 관리
3. 오늘의 강릉 관리
4. SNS 발행 관리
5. 광고 운영 관리
6. 광고 성과 관리
7. 업체 랜딩 관리
8. 홈 노출 관리

특히 “수집함 → 강릉노트 전환 → 오늘의 강릉소식 선정”이 관리자 구조의 중심이 되어야 합니다.

## 3. shadcn-admin 도입 방식 재확인

shadcn-admin 전체 설치가 아니라 필요한 컴포넌트만 선별 추출하자는 방향은 동의합니다.

다만 구현 전에 다음을 더 구체화해 주세요.

1. 어떤 컴포넌트를 가져올 것인지
2. react-router-dom 관련 코드를 어떻게 제거할 것인지
3. wouter와 충돌하지 않도록 어떤 방식으로 연결할 것인지
4. /admin/v2 라우트를 App.tsx에 어떻게 추가할 것인지
5. 기존 /admin 라우트와 충돌하지 않는지
6. 기존 ClerkProvider, fetch interceptor, pg_admin_token 흐름에 영향이 없는지

## 4. BlockNote 적용 범위 재확인

BlockNote는 관리자 전체에 적용하지 않습니다.

BlockNote는 강릉노트 본문 편집 전용입니다.

다음 구조는 동의합니다.

* GangneungNoteEditor
* GangneungNoteViewer
* GangneungNoteForm
* GangneungNoteMetaFields
* GangneungNotePreview

다만 구현 전에 다음을 보고해 주세요.

1. contentBlocks 기존 포맷 종류
2. BlockNote 포맷과 레거시 포맷이 혼재된 실제 사례
3. normalizeBlockNoteContent를 새 구조에서 어디까지 유지할지
4. 저장 시 항상 BlockNote 포맷으로 통일하는 방식
5. 사용자 상세페이지 렌더링 방식
6. OG태그 SSR과 충돌 여부
